# 多 agent 协作与维护

## 接手提示词

把本文件所在分支的 `START_HERE.md` 链接发给新agent，可附下面的文字：

> 请参与Score Function科研项目。先读取docs/handoff/START_HERE.md及其阅读清单，再查看与你任务相关的固定commit源码。先简要复述研究目标、当前方法、正负证据、未决问题和拟接手任务。把文件中历史报告的结果与当前服务器状态分开；缺数据时明确缺口。当前主协议为S10-G、sigma0.1、gamma0.1、K20，后续评测seed20260922，Flow CFG1.8，不做RL。代码、实验或解释发生变化后，请同步更新交接文档与来源。你的具体任务以用户这次指派为准。

## 分工方式

研究agent可以负责文献、问题定位、实验设计与负结果分析；工程agent可以负责adapter、运行脚本、环境排查与结果汇总。任务可调整，角色本身不赋予额外权限。不要默认另一个agent能读到当前聊天或拥有服务器访问权。

每个写代码/执行实验的任务指定一个负责人，使用独立分支/worktree。开始前核对目标文件、run和GPU组是否被其他任务占用。一个已有队列由一个控制器负责，另一个agent可以只读分析结果。不要同时改同一冻结plan或覆盖相同输出目录。

## 任务记录模板

```text
任务ID / 日期：
负责人：
目标与完成条件：
任务分支 / 起始commit：
涉及文件 / run目录 / GPU组：
输入配置、checkpoint与来源：
已完成的修改：
验证结果及适用范围：
产物路径 / commit / PR：
未解决问题：
下一步与交接对象：
```

这里的“完成条件”应具体，例如“现有68项队列的完成/失败项与summary一致，配对结果可追溯”，而非笼统的“把实验跑好”。

## 什么时候更新哪个文件

| 变化 | 更新位置 |
| --- | --- |
| 研究目标或约束变化 | RESEARCH、DECISIONS、START_HERE摘要 |
| 模型/损失/训练或adapter变化 | IMPLEMENTATION、对应代码与实验协议来源 |
| 新得分或核实旧得分 | EXPERIMENTS.csv、EXPERIMENTS.md；记录source、完整性及版本 |
| 队列启动/完成/失败/恢复 | STATUS；写明观察时间与回执路径 |
| 新分支、权重或源码快照 | SOURCES、相关manifest |
| 调度/路径/环境变化 | OPERATIONS；不要篡改历史snapshot |

每轮更新保留“事实/解释/待验证”区分。不要把完整聊天反复贴回仓库；只保存影响项目判断和复现的内容。对CSV中的缺失字段逐项补证，不用统一默认值填充未知历史信息。

## 文档与代码验证

文档变更检查链接、JSON/CSV可解析性、差值和计数一致性、来源与表述范围。纯文档整理不需要重新训练或GPU仿真。

模型或adapter变更使用仓库已有相关测试，必要时增加能覆盖实际行为的新检查，再做对应环境的小规模真实场景验证。合成CPU smoke只能说明接口可运行，不能写成真实闭环通过。必要的完整benchmark在服务器执行并记录实际回执。

## 提交约定

文档内容优先中文，代码标识符和路径保持原样。公式使用Markdown的行内/行间LaTeX。提交说明写清行为变化、证据和验证范围；待核实的服务器状态不放进“已完成”部分。

运行期间以最新日志为准，研究意图以用户最新明确决定为准。发现旧记录冲突时补充修正来源，不静默删掉负结果或把旧实验重命名成新协议。
